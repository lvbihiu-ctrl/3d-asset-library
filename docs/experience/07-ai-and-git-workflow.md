# AI 与 Git 协作经验

## 分工按能做什么划分

网页版 ChatGPT 可以梳理需求、编辑仓库代码和审核 PR；本机 Codex 负责 Windows 构建、安装、真实剪贴板、WebView2、数据保留和故障排查。用户确认视觉偏好、工作流是否实用，以及涉及真实 C4D 的关键动作。

这不是对某个产品永久权限的保证。每轮根据实际工具和权限说明能做什么，不冒充已经操作了不可访问的电脑。也不假定网页版没有额度限制，或本机 AI 一定掌握上次对话的状态。

## 每轮推进一个可交付结果

开始前写清当前故障、要改的边界、用户能观察到的完成条件、已有数据如何保留。先跑通完整小闭环，再调视觉；不要把“要不要重构、换平台、加大功能”作为每轮默认话题。

用户愿意少打字，关键偏好问题给少量有区别的选项。回答后记录，不反复 Grill 已经确认的决定。明确的修复任务直接做，缺关键授权或偏好会改变方向时才停下问。

交付时先给软件和实际效果，再给少量测试与未完成项。不要以无限审查、反复打包、安装更多 Skill 代替交付。

## 从远端与运行事实继续

1. 查看工作区与未提交改动；保存已有成果，禁止 reset/清理覆盖。
2. 同步远端 refs，检查目标分支、PR 状态、正式清单及当前实际 EXE。
3. 把“已发布”“PR待合并”“本机已试用”“仅建议”分开。
4. 独立功能分支或工作目录，保留 #15 等未完成工作；不把多个任务的脏代码混用。
5. 完成后提交有边界的 PR，说明基线与依赖；不为消除分歧强推覆盖。

“main看上去旧”可能只是没有 fetch；“本机界面很新”也可能来自未合并功能分支。两边都不能凭印象改版本或回退数据。

## 分支累积也会造成慢

功能在新分支完成，却没有把依赖和验收推进到 `v2-dev`，后续 AI 仍会从老基线开工。经验是记录精确提交、PR 覆盖到哪个功能、哪几项还未合并，而不是靠继续造更多版本弥补。

文档 PR 只带文档；不要从最新功能分支直接提交一个“文档整理 PR”，结果顺便包含所有未验收程序。仓库历史、二进制安装包和真实用户数据也不能整包上传。

## Skill 是工作方法，不是权限开关

- 需求不确定时用 grilling 类技能收敛问题；目标明确后停止重复盘问。
- 界面分析先辨认用户要什么，再看布局和实现；设计建议不替代用户偏好。
- 复杂故障用可复现、能先失败后通过的测试定位。
- 程序拆解先判断是否有源码。完整源码普通只读分析即可，不必安装反编译引擎；封装程序才选择对应 REA 路线。
- 测试与审查技能适用于相关变更，不是每轮都安装全部工具。安装 Skill 不代表 MCP、引擎或账号权限已经可用。

按当前环境可用名称和实际 SKILL.md 使用，不把旧聊天里的技能名当成一定已安装。修改 Codex 模型、默认配置或认证也不能凭回复声称成功，应验证实际能力；本项目不保存账号认证材料。

## 可复制的交接内容

每次交接至少包含：目标、当前分支/提交、PR、实际运行成果、测试与失败、数据/旧版本保护范围、下一项具体验收。GitHub 放脱敏结论与代码，不放整段私聊、客户文件、MCP Bearer、个人令牌或本机认证文件。

已有分工约定见[协作说明](../AGENT_COLLABORATION.md)。其中面向未来的门禁和任务计划不代表所有功能已经实现，当前事实见[状态页](08-current-state-and-next-steps.md)。
