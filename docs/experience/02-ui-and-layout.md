# 界面与布局经验

## 把自适应说清楚

用户想要“错落但紧凑”：图片保持原比例，横图自然变矮、竖图自然变高；列数和列宽适应素材区；选中、搜索、拖拽和缩放不打架。这与统一画框网格、浏览器全页缩放、无限画布是不同能力。

RenderCommander 的整齐主要来自固定 16:10 画框、裁切铺满、小卡片和精简文字。可以借鉴间距与文字层级，但不能因为它更整齐就把完整渲染图裁掉。用户看过分析后仍选择瀑布流。

## 布局失败与修正

| 观察到的问题 | 原因 | 保留的经验 |
|---|---|---|
| 两张卡片全叠在第一列 | 原 CSS 多列没有得到期望的分布 | 使用明确的最短列放置，覆盖稀疏结果测试 |
| 只有两条记录却巨大 | 为填满容器无限拉伸 | 少量结果保持紧凑，不强制铺满 |
| 大库右侧一块空白 | 列宽锁定像素，剩余宽度未分配 | 足够记录时各列均分宽度，保持固定列间距 |
| 横图上下、竖图两侧空边 | 项目参考图强制放进 4:3 框 | 瀑布流中参考图和模型封面都使用真实比例 |
| 无封面的卡片很长 | 占位图与长目录文本占满卡片 | 紧凑占位；标题限行；路径摘要，完整值放详情/提示 |
| 缩放连侧栏文字一起变 | 浏览器页面缩放 | Ctrl+滚轮仅改素材卡片目标大小 |

最短列排版必须在图片解码、区域宽度、布局或筛选结果变化后重新计算。不要只在首次页面加载时算一次。

## 已实现的缩放取舍

当前试用提交默认目标宽度 260px，保存范围 160–480px。Ctrl+滚轮在素材区改变目标密度，侧栏和页面整体比例不变，偏好重开后保留。

目标宽度不是每次都等于实际列宽。窗口容纳完整多列时，需要均分剩余宽度；相邻一次滚轮可能还没有跨过列数变化点。测试应同时检查偏好保存和实际布局，不能强迫每次都精确增减相同像素。

## 大库不能只测试两张图

真实库使用每页最多 80 条，搜索和筛选先对完整索引执行，再分页。分页是当前实现，不是已经实现虚拟滚动。图片尚未解码时截图会失真；只凭文件名“1920x1080”也不能证明截图像素正确。

至少覆盖 820×600、1016×689、1920×1080；深浅主题；少量/满页；长标题；缺图；横竖极端比例；窗口缩放；相同参考图重复记录。检查右边界、列间距、不重叠、不裁切和选中反馈。

## 不靠换框架解决排版

V2 继续使用现有 .NET 10 + WebView2，界面由 HTML/CSS/JS 呈现。漂亮网页可以进入桌面窗口，但还要接原生扫描、剪贴板、定位和 FileDrop。单纯套壳不等于功能接通，也不需要为了借鉴另一个工具而切到 Electron。
