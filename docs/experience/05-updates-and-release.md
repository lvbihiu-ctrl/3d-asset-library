# 更新与发布经验

## 运行中的 EXE 不能自我覆盖

早期失败出现 `.exe.new` 重命名到正在使用的 EXE 时 Access denied。修复要先分清桌面快捷方式指向谁、实际运行进程、旧安装逻辑与文件权限，不能靠反复下载同一个安装包解决文件锁。

旧客户端已经形成“启动器＋可替换脚本”更新机制，V2 本机安装使用独立版本目录。两者都避免直接覆盖运行文件，但不是同一条发布通道。

## 版本号不是完整升级证据

v0.1.5 用白天/夜晚切换作为显眼标记。用户亲自完成旧客户端点更新、下载校验、安装重启，再确认新功能和两条旧记录/封面保留。这个方法比只比较版本字符串更能发现“拿到清单但程序没换”的问题。

完整升级至少记录：出发版本、发现更新、下载来源、实际字节校验、安装目标、旧进程退出、新进程路径、新功能可用、数据保留和失败恢复。若只做了本地启动跳转，就只能叫启动演示。

## 清单发现与程序下载分开

正式 v0.1.7 的规则以[OTA 协议](../UPDATER_PROTOCOL.md)为准：清单需要发现最新状态，下载内容需要不可变。

1. 清单请求添加随机防缓存参数和禁缓存头。
2. Raw 未发现更高版本或失败时，用 GitHub Contents API 独立确认；不能把网络失败说成已是最新版。
3. 程序脚本 URL 固定到本仓库完整 40 位 Commit SHA，而不是浮动分支。
4. SHA256 校验下载到的真实字节；不匹配不安装。
5. 发布顺序是先提交并测试程序，再获得固定提交和真实哈希，最后更新清单。

公开仓库下载不应新塞个人令牌或要求用户配置 API Key。匿名限额、网络错误与仓库权限仍要有明确错误提示，不能靠隐藏失败“保持顺滑”。

## SHA256 必须对应发布字节

Windows Git 检出可能把 LF 变成 CRLF，UTF-8 BOM 也改变哈希。源码文本相同不代表文件字节相同。本项目 v0.1.6/v0.1.7 已踩过这个坑：应校验仓库原始对象或固定提交 Raw 下载的最终字节，不能盲用 Windows 工作目录的 Get-FileHash 值填清单。

固定 Commit SHA 由 Git 获取，文件哈希由程序计算；不要让聊天模型凭空编造。已有发布完整性 CI 会核对 URL、SHA256 与版本。它是校验门禁，不代表“只改一个脚本就自动递增版本并发布”的工作流已经落地。

## 自动回滚不能只留一份旧文件

完整的自动回滚还需要启动健康判断、失败信息、恢复正确入口、避免回滚循环，以及数据格式兼容。只有备份文件或快捷方式回退，不能叫任意新版本崩溃都能自动恢复。

用户提出过自动生成清单、last-good 启动回滚，尚不能把这些建议写成已完成。独立 V2 更新器曾 A→B 成功、B→C 验收失败并恢复 B，因此两次连续升级门槛仍未通过。

## 当前保护边界

正式 v0.1.7 和 `desktop-updates/native/latest.json` 不因 V2 试用而修改。V2 正式更新、旧版到 V2 桥接、回滚与签名必须单独验收；本机切快捷方式不能替代它们。本轮经验归档不发布软件版本。
